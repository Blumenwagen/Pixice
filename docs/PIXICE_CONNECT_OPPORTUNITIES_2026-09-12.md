# Pixice Connect opportunities

Reviewed 12 September 2026. This review covers the product behavior and source code, with proposals for future work.

I would make Connect a dependable way to leave the computer running and continue work from another device. The backend already supports most of the application. The largest opportunities are reliable access, a useful phone experience, and clear answers when a connection drops during an action.

Connect already includes task creation, follow-ups, steering, approvals, model and permission choices, project files and editing, Git review, Board, workflows, Tools, remote browser control, and Unified Usage. Its independent backend continues after the desktop interface closes. The current boundary is a trusted operator of the whole host. [Connect 02](decisions/connect-02-remote-workspace.md) and [Connect 03](decisions/connect-03-independent-backend.md) supersede the earlier monitoring-only proposal.

| Order | Improvement | Concrete experience | Suggested scope |
| --- | --- | --- | --- |
| 1 | Reliable everyday access | Scan a QR code, pair the phone, and use the same address next week. See when access will expire before it interrupts work. | Add QR output to existing single-use links, a setup checklist with connection diagnostics, guided permanent-endpoint setup, expiry warnings, and explicit renewal. Existing permanent endpoints are manually configured today. |
| 2 | A mobile attention inbox and installable web app | Open Pixice from the phone's home screen, see which tasks need a decision, answer, and return to what you were doing. Receive an optional notification while the app is closed. | Add an app manifest, a service worker for the app shell, large approval/question controls, and host/project/thread deep links. Add Web Push as a separate opt-in delivery path with generic notification text and fresh request validation after opening. |
| 3 | A cross-host overview | See running, waiting, failed, and completed work across paired computers. Jump directly to a task or choose where a new task should run. | Extend the existing saved-instance and Unified Usage patterns with bounded status summaries. Show last successful contact and partial failures. Keep execution and provider sessions on the selected host. |
| 4 | Recoverable command outcomes | After losing a connection while starting a task or answering an approval, see whether the host accepted the action. | Retain command IDs on the client and add an authenticated read-only outcome lookup. Show pending, completed, failed, or unknown. Never automatically resend an uncertain command. |
| 5 | Reliable file transfers | Attach several files with an accurate total limit and visible progress. Download generated artifacts to the device being used. | First enforce the actual encoded request budget before sending. Later introduce bounded uploads with attachment IDs, cancellation, cleanup, and resumable transfer where useful. Resume transfer bytes without automatically submitting a task. |
| 6 | A better remote browser | Read small text with zoom, choose quality or reduced-data mode, and get a clear indication when the displayed page is stale. | Begin with adaptive capture pacing, quality controls, capture metrics, and interaction-triggered refresh. Then consider bounded drag gestures and a semantic links/forms view for accessibility. Preserve frame freshness and navigation validation. |
| 7 | Host readiness and compatibility | Know that a host is online but its browser helper is missing, or that an older host cannot run a particular feature. | Add an authenticated capability/readiness response. Use it to explain unavailable controls and advertise transfer limits and supported transports. Keep identity discovery small and public; keep detailed readiness authenticated. |
| 8 | Limited device access | Pair a phone for viewing selected projects without giving it the same access as a trusted desktop. | Treat this as a separate authorization project. Start with observer access and an explicit project allowlist. Enforce scope on reads, events, files, browser sessions, and commands on the host. Hiding controls alone is insufficient. |

The first three would make the biggest difference to everyday use. Command outcome recovery belongs alongside them because a phone regularly changes networks or suspends the browser.

Pairing and endpoint work can build on [ConnectionsSettings.jsx](../src/connect/ConnectionsSettings.jsx:53), which currently offers a temporary tunnel, a manually entered endpoint, and a copyable pairing link. Device credentials expire after 30 days, and the settings page already receives their expiry timestamps. A renewal flow needs an explicit identity and revocation policy; merely extending a bearer token forever would undermine that expiry.

The mobile app is a substantive new capability. [index.html](../index.html:1) has no web-app manifest, and the client entry point has no service-worker registration. Current notification delivery goes through the host's native helper in [application.mjs](../electron/backend/application.mjs:2500). WebKit documents Web Push for home-screen web apps on iOS and iPadOS, with permission requested after direct user interaction. This makes a phone web app feasible, subject to verification on real devices. [WebKit documentation](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/).

Cache the app shell and unsent drafts first. A cached approval is never authority to execute an action. A sleeping or offline host also cannot execute a remote action or originate a new notification until it is running again.

The multi-host view has a useful starting point in [unified-usage.js](../src/connect/unified-usage.js:145). It already handles host identity deduplication, bounded timeouts, concurrent reads, cached measurements, and partial failures. Reuse those patterns without opening a full workspace and event stream for every host.

I found the following issues worth resolving before expanding the remote workload. These are source findings unless a reproduction is explicitly stated.

| Priority | Finding and evidence | Expected fix and verification |
| --- | --- | --- |
| High | All public API requests share a 1,200-request/minute budget keyed by socket IP, charged before authentication. The supported loopback proxy makes clients share that address. Polls finish as events arrive and immediately start again. See [server.mjs](../electron/connect/server.mjs:200), [poll delivery](../electron/connect/server.mjs:183), and [application-client.mjs](../electron/connect/application-client.mjs:58). | Separate unauthenticated limits from authenticated device allocations. Reserve capacity for approvals and interrupts, and bound event delivery frequency. Measure several streaming tasks and clients with browser preview enabled. The code shows a throttling risk; this review does not establish a measured production outage. |
| Medium | A command racing a backend restart receives HTTP 409 before execution. The client maps every 409 to unauthorized, so the UI temporarily asks the user to pair again. Polling normally repairs the state. See [server.mjs](../electron/connect/server.mjs:291), [client handling](../electron/connect/application-client.mjs:53), and [status label](../src/connect/ConnectRoot.jsx:171). | Give errors machine-readable codes. Distinguish stale backend identity, other conflicts, and expired/revoked credentials. Reconcile state without replaying the command. Test a command sent with the previous backend generation. |
| Medium | The composer accepts ten attachments of up to 25 MiB each, but Connect accepts only 48 MiB for the whole JSON body. Two 20 MiB binary files already exceed that after base64 encoding. See [composer limits](../src/App.jsx:71), [attachment selection](../src/App.jsx:2859), and [server body limit](../electron/connect/server.mjs:13). | Calculate aggregate encoded size and give a useful error before sending. Test multiple individually valid files at the total boundary. The longer-term transfer API should avoid building one large base64 JSON request in memory. |
| Medium | Remote saved-receipt reads require a live provider thread lookup before reaching the durable receipt handler. The handler itself already checks the receipt's project. See [remote validation](../electron/connect/remote-operations.mjs:40), [provider lookup](../electron/connect/remote-operations.mjs:15), and [receipt handler](../electron/backend/application.mjs:1203). | Authorize saved receipt reads against durable project ownership. Verify that results remain readable with the provider unavailable and that a mismatched project still fails. |
| Medium, needs reproduction | Host switching moves all workspace values through shared, unscoped localStorage keys. Two same-origin browser tabs on different hosts can interfere with those values. Current coverage tests sequential switching only. See [switchInstanceStorage](../src/connect/ConnectRoot.jsx:13) and [existing test](../tests/connect-client.test.jsx:116). | Store workspace data directly under host-specific keys, with the active workspace selection scoped appropriately per tab. Reproduce with two tabs, simultaneous draft edits, reloads, and rapid host switching before changing the storage model. |

Command outcome recovery can start small. The server already stores each command's hash, promise, and result under device ID and command ID in [server.mjs](../electron/connect/server.mjs:302). The client currently generates the ID inline and discards its usefulness after a lost response in [application-client.mjs](../electron/connect/application-client.mjs:48). A result lookup can resolve same-process response loss. Durable receipts across restarts require additional persistence and must retain an honest unknown state when execution cannot be proven.

For browser performance, [RemoteBrowserSurface.jsx](../src/connect/RemoteBrowserSurface.jsx:33) requests a frame and waits 500 ms before requesting another. Hidden clients already pause capture. The host captures JPEG at fixed quality 72 in [remote-browser.mjs](../electron/browser/remote-browser.mjs:86). Measure capture time, bytes per minute, and input-to-visible-result latency before selecting a different transport. Adaptive pacing and reducing unchanged frames are smaller steps than introducing video streaming.

Keep long polling supported. Although the host already has an SSE endpoint, Cloudflare explicitly says Quick Tunnels do not support SSE. A future streaming client should negotiate or probe support and fall back without losing event ordering or recovery. [Cloudflare Quick Tunnel limitations](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/trycloudflare/).

I would deliver this in three increments:

1. Fix recovery messages, aggregate attachment validation, saved-receipt access, and request-budget fairness. Add QR pairing, expiry indicators, and useful connection diagnostics.
2. Add the installable phone experience, task deep links, opt-in push, command outcome lookup, and the cross-host attention overview. Verify the complete loop on real phones, including suspension and network changes.
3. Improve browser interaction and file transfers. Consider limited device roles or remote simulator preview as separately scoped expansions. The simulator backend already exists, but the remote client deliberately excludes it today in [client.js](../src/connect/client.js:60).
