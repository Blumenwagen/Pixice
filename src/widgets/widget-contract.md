# Live widget frontend contract

`window.pixice.widgets` is the transport-neutral API. Each project-scoped call takes `{ projectId }`. Local desktop and Connect clients share the same widget methods. TypeSafe credential methods are host-only and are not in the public Connect protocol.

| Method | Payload | Result |
| --- | --- | --- |
| `list` | `{ projectId }` | `{ data: ProjectWidget[] }` |
| `draft` | `{ projectId, text, requestId?: UUID, context?: { projectName?: string } }` | `WidgetDraftResult` |
| `cancelDraft` | `{ projectId, requestId }` | `{ cancelled: boolean }` |
| `commit` | `{ projectId, spec }` | `ProjectWidget` |
| `update` | `{ projectId, widgetId, spec, expectedRevision }` | `ProjectWidget` |
| `updateUserState` | `{ projectId, widgetId, userState, expectedRevision }` | Updated v2 `ProjectWidget` |
| `readSource` | `{ projectId, widgetId, source }` | `{ data: projectedRows[] }` |
| `delete` | `{ projectId, widgetId }` | Deleted `ProjectWidget` |
| `keyStatus` | none | `{ configured: boolean }` |
| `keySave` | `{ key }` | `{ configured: true }` |
| `keyRemove` | none | `{ configured: false }` |

A `WidgetDraftResult` is `{ status: 'draft', projectId, spec, candidate }` or `{ status: 'fallback', reason }`. Fallback reasons are `key_missing`, `credential_error`, `no_candidate`, `low_confidence`, `service_error`, `timeout`, and `cancelled`. On fallback, keep the composer text and continue normal chat. Drafting makes one TypeSafe decision call and does not persist or act on anything. The host ignores renderer supplied project context except the project ID and sends only its project display name to TypeSafe.
Supply a fresh `requestId` if the UI may cancel a pending draft. `cancelDraft` aborts only a matching project request. Drafts time out after 10 seconds.

`WidgetSpec` is validated JSON: `{ version: 1, title: string, size?: 'small' | 'medium' | 'large', blocks: WidgetBlock[] }`. Version 1 permits one to eight blocks. `size` is an optional initial display size, independent of block type and item count. Explicit requests such as "small checklist", "medium widget to count laps", or "large timer for 5 minutes" set it during draft composition when the request provides enough content for a widget. Without an explicit size request, Pixice omits the field and the frontend chooses its default. Existing stored specs without `size` remain valid. The WidgetShelf should use a user's persistent local resize override first, then `spec.size`, then its default. Each block is one of:

- `{ type: 'timer', label, durationSeconds, endAt }`. Duration is an integer from 1 to 2,592,000. `endAt` is an ISO timestamp or null in a draft or update request. Commit and update start or restart any timer with null `endAt` on the host and return a persisted end timestamp. Render remaining time as `max(0, Date.parse(endAt) - Date.now())`; interval ticks update display only and never call Jev. To restart, update with null `endAt` and the current revision. An explicit timestamp remains unchanged.
- `{ type: 'checklist', label, items: [{ id, text, done }] }`. Item IDs are UUIDs. Toggle `done` locally, then call `update` with the full spec and current revision.
- `{ type: 'counter', label, value, step }`. Increment or decrement locally by `step`, then call `update` with the full spec and current revision.

A `ProjectWidget` adds `id`, `projectId`, `revision`, `createdAt`, and `updatedAt`. `update` rejects stale revisions. Refresh via `list` and reconcile user changes if another client edited the widget. Calls reject invalid JSON, unknown project IDs, and cross-project widget IDs. Connect observers cannot call widget operations. The TypeSafe key never appears in status, draft, widget records, events, or errors.
Commit and update validate `size` when supplied and persist it with the spec. Resizing in WidgetShelf stays local; it does not change `spec.size` unless a caller deliberately submits an updated spec.
Commit, update, and delete emit `WidgetUpdated` with `{ projectId, widgetId, action }`, where action is `committed`, `updated`, or `deleted`. Clients can refresh the project list on this event.

Composition uses the official `POST https://api.typesafe.ai/v1/systemone` endpoint with `model: 'jev-latest'`, one `state`, and typed Noul, Choice, and Score questions. Pixice extracts concrete block candidates from the request. Jev decides which blocks fit, selects a lead, and rates overall usefulness. Pixice combines the selected blocks and validates the resulting spec before returning it. The frontend must never infer that a draft is committed.
The Score answer needs a valid confidence of at least 0.65 as well as a useful score. Lower or missing confidence returns `low_confidence` fallback. Checklist instructions such as `Make a checklist:` are excluded from the item list.

## v2 composable documents

`widget-schema.mjs` defines Pixice's v2 document parser. The host drafts eligible Board and calculator requests with the existing TypeSafe key, validates and stores v2 documents, and serves declared Board sources through `readSource`. The Focus shelf renders both versions. A v2 user's scalar edits go through `updateUserState` with a required revision. Upstream json-render uses Zod 4; Pixice's contract remains on Zod 3.25.76.

The top level is `{ version: 2, catalogVersion: 1, title, size?, root, nodes, state, sources, derived, actions }`. `size` is `small`, `medium`, or `large` and is independent of the tree. `nodes` is a flat array with stable `id` values. Each node has a catalog `type`, literal or bound `props`, named `slots` containing child IDs, and an `on` map from catalog event names to action IDs. The root has no parent; every other node has exactly one. Unknown components, props, slots, events, missing children, duplicate IDs, cycles, unreachable nodes, reserved keys such as `constructor` and `prototype`, and depth over eight fail validation. `catalogVersion` pins the component definitions. `createWidgetV2Schema(catalog)` accepts a catalog registry so a future renderer can add components without editing a central type switch.

`state.user` holds persisted user input; `state.view` holds transient presentation state. Both hold named string, finite number, or boolean values. A binding is `{ path: '/user/name' }`, `{ path: '/view/name' }`, `{ path: '/data/source' }`, or `{ path: '/derived/name' }`. The parser checks existence and prop type. Data comes only from declared sources. Version 1 of the source catalog allows `board.list` with empty arguments and `manual`, `onOpen`, or `event` refresh. `/data/<board-source>` has `boardRows` type. The Board source adapter projects results into rows with only `id`, `title`, `description`, `column`, `threadId`, and `updatedAt`. No owner, schedule, or blocked state is inferred. `filterRows` produces `boardRows` and accepts one of those fields with a string comparison. Derived references may depend on other derived values but cannot cycle.

Arithmetic expressions use `{ op: 'add' | 'subtract' | 'multiply' | 'divide', left, right }`; each operand is a finite number or a typed binding. The composer represents parentheses as named derived steps. For example, `(hours * rate) + fee` is `subtotal: { op: 'multiply', left: { path: '/user/hours' }, right: { path: '/user/rate' } }` followed by `result: { op: 'add', left: { path: '/derived/subtotal' }, right: { path: '/user/fee' } }`. A literal `12 + 8` needs only one derived value and a `Number` result. An explicitly variable operand uses a matching `NumberInput`, `/user` value, and numeric assign action. The formula is prompt-specific; the budget document is one example, not a required template. The schema rejects nonnumeric operands, cycles, non-finite literal operands, and a literal zero denominator. A variable denominator may become zero after an edit. The runtime selector must then return an unavailable numeric result, represented by `null`, and propagate `null` through dependent arithmetic. A `Number` view must show a readable unavailable state, keep the inputs editable, and never display `Infinity` or `NaN` or crash. The same `null` behavior applies when finite inputs overflow during evaluation. This is an evaluation result only; persisted state and document number literals remain finite numbers.

Actions are declarations, not code. `set`, `toggle`, `increment`, and `assign` can write only existing `/user` or `/view` scalar state with matching types. `assign` reads a control's `value`, `checked`, or numeric `number` event payload. `NumberInput` requires a numeric `/user` value binding and a matching `change` action with `input: 'number'`. A future executor must reject non-finite numeric event values and enforce any input bounds before writing state. `refresh` can target only a declared source. There are no URLs, scripts, arbitrary commands, or write capabilities in this foundation. A future executor must apply its own project scope and permission checks before invoking any source or action.

The catalog spans layout (`Stack`, `Grid`, `Card`), content (`Text`, `Heading`, `Number`), controls (`Button`, `TextInput`, `NumberInput`, `Select`, `Toggle`), collections (`Table`, `List`), visualization (`BarChart`, `Progress`), and utilities (`Timer`, `Checklist`, `Counter`). These are allowed document nodes, not a promise that every node has an interactive editor. The v2 renderer shows Timer and Checklist values read only. Counter controls appear only for matching increment actions. The composer builds supported prompt-derived candidates from vetted parts and returns chat fallback for malformed, ambiguous, or unsupported requests. The parser caps the serialized UTF-8 document at 128 KiB, with 64 nodes, eight tree levels, and per-node maps of at most 16 props, eight slots, and eight events. It also caps sources at eight, derived values at 24, actions at 32, keys per state scope at 32, and scalar strings at 500 characters. The Board source adapter enforces a 200-row cap.
